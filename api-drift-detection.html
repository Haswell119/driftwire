Is your live API still matching your spec?

Spec drift is the gap that grows between what your OpenAPI spec documents and what your API actually returns. It's the single biggest source of integration bugs — and almost nobody checks for it.

What spec drift looks like

  • A field is renamed in code but the spec still lists the old name — clients read the wrong key.
  • An endpoint starts returning a field that isn't in the spec — generated clients drop it.
  • A value type changes (string → integer) and only the consumers notice.
  • A documented enum gains or loses values without a spec update.

Why spec-vs-spec tools miss it

Most drift tooling — including the popular oasdiff — compares two spec files. They explicitly cannot tell you whether your live API matches your spec, because they never touch a running endpoint. That's the gap DriftWire fills.

Check spec vs. reality in one command

# probe live endpoints and validate every response against the spec
driftwire check openapi.yaml --url https://api.example.com
# reports type mismatches, undocumented fields, missing required,
# and enum violations — exit 1 when drift is found

Run it locally during development, or as a CI step that gates deploys the same way unit tests do. No uploads, no telemetry, no account — responses never leave your machine.
